| R-01 | Major | aidlc/spaces/default/intents/260930-sentiment-v1/inception/domain-design/components.md > SentimentEngines depends_on Configuration and AnalysisService depends_on Configuration | Two components own the same decision. SentimentEngines reaches Configuration to "Reads mode, model and key before choosing an implementation", while AnalysisService reaches Configuration to "Reads the resolved mode for its dispatch decision", and both behaviour blocks claim the live-without-key refusal (Configuration: "a refusal only when a live analysis is attempted"; AnalysisService: "refuses a live attempt when live was requested and no key is usable, naming the config file"). The boundary this must map onto is the opposite: the CodeKB states "Only Analysis Orchestration may choose an engine" (codekb/very-cool-sentiment-analysis/component-inventory.md, ownership rule 2, citing app/service.py:60-82), and decisions.md ADR-003 itself claims the dispatch point is "the single place where mode resolution takes effect". traceability.json's US5.1 target (Configuration, SentimentEngines, WebSurface) also omits the component the catalogue says resolves the mode. A developer cannot tell which component implements the FR5.1 credential precedence and the FR1.3 refusal. | Name one owning component for mode and engine resolution and for the live-without-key refusal, make the other component consume that answer instead of re-deriving it, and align the components.md dependents, ADR-003 and the US5.1 traceability target with that owner. | New |
| R-02 | Major | aidlc/spaces/default/intents/260930-sentiment-v1/inception/domain-design/decisions.md > ADR-003, with components.md > AnalysisService depends_on SentimentEngines (style: event) | The event handoff is recorded but has no home and no message shape. AnalysisService depends on SentimentEngines with "style: event" while every other edge in the catalogue is plain sync, yet no component's behaviour or responsibilities claims the in-process dispatcher the ADR introduces, and SentimentEngines declares entities: [] so neither the published request nor the typed result crossing that seam has an owner or a shape (only three entities are captured in the whole catalogue). ADR-003's Alternatives Rejected turns on "rejects the human's decision" rather than the trade-off on this path - the step it replaces is one in-process call on the request thread (app/service.py:103) for a synchronous single-user localhost flow - and it is silent on the lifecycle questions the style raises: the dispatcher's scope and lifetime, and what carries a failure back. Functional Design would have to invent the mechanism. | Record where the in-process dispatcher lives, which component owns it and its scope, capture the request/result message shape as an owned entity (or state explicitly that it is a value rather than an entity), and add the concrete trade-off against the synchronous call to ADR-003. | New |
